| 寬度 | 390 px 與 1280 px 都要檢查 |
| 不可輸出 | 密碼、cookie、session、hook 指令、webhook 網址（沿用 `status` 的做法） |

### 寫入保護提案

目標：網頁伺服器不能變成其他本機程式（包括 agent）或惡意網站可以呼叫的無驗證寫入 API。

1. **只綁 127.0.0.1，並檢查 `Host`**：只接受 `127.0.0.1:<port>` 與 `localhost:<port>`，其他一律 421。所有請求（包括讀取）都檢查，防止 DNS rebinding 讓外部網站讀取分數。
2. **不回應 CORS**：沒有 `Access-Control-Allow-*` 標頭；跨網站的腳本讀不到回應。
3. **啟動權杖**：`ilearn web` 每次啟動產生 32 位元組隨機權杖，只放在記憶體，不寫入檔案、log、`status` 或 MCP。開啟瀏覽器時網址帶權杖，第一次請求換成 `HttpOnly`、`SameSite=Strict` 的 cookie，再轉址去掉網址中的權杖。
4. **寫入必須同時符合**：`POST`；有效 cookie；`Origin` 等於本伺服器；自訂標頭 `X-Ilearn-Action`（跨來源請求必須先 preflight，而伺服器不回應 preflight）。
5. **與 `mark-teammate` 一致的 TTY 規則**：只有在互動終端啟動的 `ilearn web` 才開放寫入；非互動啟動（例如 agent 的 shell）只提供唯讀頁面，寫入回傳 403「只能由本人在互動終端啟動的網頁操作」。
6. **網頁不提供的寫入**：hook 指令與 webhook 網址（可執行任意指令）、帳號密碼與登入。這些只顯示狀態，修改留在終端（Phase 7）。
7. **限制說明**：同一使用者的程式本來就能直接改 `rules.yaml` 或資料庫；此設計的目的只是不新增一個更容易被呼叫的寫入入口。

## 8. 建議

建議 **方向 A**，前後端採 **伺服器端產生 HTML**（A、C 的做法）。

理由：

1. 首頁「課表＋重要通知」是設計書中已由使用者確認的決定，A 照做，B 需要推翻。
2. 伺服器端產生 HTML 不新增套件、不需要打包工具，測試可直接呼叫 handler 比對輸出；Phase 5 的 Electron 可以直接載入同一個本機網址，JSON API 的好處有限。
3. 以真實資料調整 A 的缺點：390 px 把「需要處理」放在課表之前；課表只顯示有課的節次列；沒有上課時間的 3 科列在課表下方。

開始實作前需要另外決定：

| 題目 | 選項 |
| --- | --- |
| 首頁公告範圍（沒有發布時間、沒有已讀） | 新增「已讀」狀態；或同步時補存公告發布時間，只顯示 7 日內 |
| 網頁可改的設定範圍 | 只做設計書列出的規則、公告分類、隊員已交、Reload；夜間時段、提醒時間、每科覆寫是否也在 Phase 4 |
| 規則全部停用 | 是否為刻意選擇；若否，另開工作讓設定精靈第 6 步在全部取消時再確認一次 |

| 3 | 提醒 | 系統提醒（登入過期、同步不完整、規則全部停用、推送失敗）、7 日內即將發出的截止提醒、重要公告 |
| 4 | 課程設定 | 左欄選課程，右欄為該科的規則覆寫、截止提醒覆寫、摘要（Phase 6 開放） |
| 5 | 系統設定 | Reload、同步狀態、推送方式（只顯示狀態）、夜間時段、截止提醒、通知規則（含試算）、帳號（只顯示狀態）、Reset |

課程版面：左欄為區塊清單（待辦、已完成、考試、公告、教材檔案、影片、問卷、分數與評語、課程資訊，空區塊顯示「沒有」），右欄為選中區塊的內容；待辦內逾期另列，小組作業可剔選「隊員已交」。

### 顯示規則

### 其他決定
